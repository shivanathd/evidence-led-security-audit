# Optional profile: PHP security release of 2026-10-21

Last checked: 2026-10-22. This profile is a dated snapshot, not a standing rule. On every run, re-read the primary sources below and record their `retrieved_on` dates. If a source has changed, the source wins and this file is out of date. Never treat these versions as the "latest" forever.

## Primary sources

- PHP project announcement: [php.net news archive, 2026-10-21](https://www.php.net/archive/2026.php#2026-10-21-5) and the security advisory on the [php.net front page](https://www.php.net/) (who is at risk, how to update, interim measures)
- CVE-2026-109618, RCE via OOM corruption: [GHSA-w8hw-w9fx-j79w](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w)
- CVE-2026-109619, RCE via stale global state: [GHSA-6wmf-4rv5-p3rp](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp)
- For distribution or LTS builds: that vendor's own advisory for the exact package and build. Record it with `kind: vendor_advisory`.

## Fixed upstream versions (as of the date above)

The advisories list fixed versions 8.5.12, 8.4.27, 8.3.36 and 8.2.35 ([OOM advisory](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w), [stale-state advisory](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp)).

- The current support table lists PHP 8.2 security support through 2026-12-31; refresh that table during a real audit ([PHP supported versions](https://www.php.net/supported-versions.php)).
- Distributions and LTS vendors received the patches before release, so a vendor package may already carry the fix under a different version string.
- PHP 8.1 and older get no upstream releases. The PHP security team published minimal source backports for 7.4, 8.0 and 8.1 for people who build from source; record which one was applied, and to which build. Otherwise verify the vendor's maintenance and patch evidence or plan an upgrade. Do not infer a backport from a package version alone.
- Products and appliances that embed PHP are affected through their own builds. Track the product vendor's advisory, not the upstream version.

Comparing version strings is only valid for upstream builds:

- A distribution build such as `8.3.6-0ubuntu…` or `php8.3-fpm 8.3.36-1~vendor` needs package and advisory evidence for that exact build (`vendor_patch` route).
- A source-backport build needs evidence that the patch was applied to the build you are running.

## SAPI exposure: record it per advisory, not as one claim

php.net lists every PHP installation that serves web requests as at risk (FPM, mod_php, php-cgi, FrankenPHP and LiteSpeed), with mod_php highest. Inventory every serving PHP runtime, then derive exposure from the full advisory and the actual SAPI, build and application path. The advisories describe different levels of demonstrated and conditional exposure, so record each separately:

| SAPI | CVE-2026-109618 (OOM) | CVE-2026-109619 (stale state) |
| --- | --- | --- |
| mod_php | Validated over HTTP | Confirmed (fatal backtrace path on 8.5; session upload progress) |
| FPM | Susceptible by source analysis; no complete exploit shown | Session-lifecycle path validated. The INI-diagnostic path applies only if the frontend sends `PHP_VALUE`/`PHP_ADMIN_VALUE`. |
| LSAPI | Likely; application-specific; not validated | Conditional candidate |
| FrankenPHP | Likely, by source analysis | Not established in the default configuration. That does not mean immune. |
| php-cgi | Listed at risk by php.net; no validated path in the advisory: record at risk, path UNKNOWN | Listed at risk by php.net; record at risk, path UNKNOWN |
| CLI | Not stated: record UNKNOWN. Workers that parse untrusted input still need review. | Not stated: record UNKNOWN |

Sources: [GHSA-w8hw-w9fx-j79w](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w), [GHSA-6wmf-4rv5-p3rp](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp) and the [php.net advisory](https://www.php.net/).

Do not record every web-serving SAPI as equally exploitable. Do not mark a SAPI as unaffected because its row says "not established" or "not stated".

## Runtime proof

- `php -v` reports the CLI binary. It does not prove what FPM, mod_php, CGI, FrankenPHP or LiteSpeed runs. Capture the version and build from the serving runtime itself. Use one of these:
  - an owner-run, read-only query inside a running worker
  - the package database in the deployed image digest, mapped to that runtime
- Never add or call a public `phpinfo()` or status endpoint to collect this.
- Record each listener and pool separately, including secondary pools, admin vhosts and sidecars. One pool's version proves nothing about the others.

## Emergency measures are risk reduction, not fixes

The full advisories identify the patched release as the complete fix and explain why configuration measures are incomplete ([OOM advisory](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w), [stale-state advisory](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp)). Record any of the measures below as `mitigated`, with evidence of the effective configuration. Never record them as `fixed`.

Do not apply any of these automatically. Each is an owner decision.

- **`memory_limit=-1`**, enforced administratively (for example with `php_admin_value`). Check that no pool, directory or application setting puts a finite limit back.
  - This removes the controllable limit, but allocator failure can still reach the vulnerable path.
  - It also changes availability risk by removing PHP's per-request limit; memory use is then constrained by other configured boundaries. Any frontend and per-worker memory policy requires owner review and does not replace the patch.
- **Low `post_max_size`**: php.net suggests `8M` when the application takes no uploads and `32M` when it does, with `upload_max_filesize` below it. Enforce decoded request size, input field count, multipart part count, header count and nesting depth at the web server or proxy too, including for requests without a usable `Content-Length`. If the application never takes multipart form data, block it at the frontend.
- **Container or cgroup limits** are an availability boundary only. A group-wide kill can take down the master and every worker. Do not substitute `RLIMIT_AS` or `RLIMIT_DATA`: both can trigger the vulnerable allocation failure.
- **`session.upload_progress.enabled=0`** must be set in `php.ini`, a pool or server configuration that applies before request parsing. `ini_set()` or `.user.ini` is not enough. Restart every worker, and capture evidence of the restart for each pool.
- **`fatal_error_backtraces=0`** (PHP 8.5 only) needs a restart of every worker. It blocks only the confirmed backtrace path.
- **`pm.max_requests=1`** reduces same-worker reuse at a performance cost. It does not fix the issue.
- **Per-request settings that emit diagnostics before initialization** (invalid or deprecated values) should be removed. Hiding diagnostics with `error_reporting`, `display_errors` or `@` does not help.
- **Attacker-reachable fatal errors and execution timeouts** (callbacks, upload or import processing, cleanup) are application fixes, tracked as their own findings.
- **Log review**: finding no errors in the logs is not proof of safety.

## Closing a finding under this profile

Use `verification_basis: vendor_patch`. No exploit reproduction is needed or wanted. Record all of the following:

- `package` and `fixed_build`
- package-advisory evidence linked to a primary source
- evidence that the fixed build is installed in the deployed image digest and observed on each serving runtime
- application regression tests

A source change such as a Dockerfile edit does not close the finding until the deployed image digest and the running workers show the fixed build.

The current JSON closure gate expects an image-based provenance chain. On bare-metal or managed PHP without those fields, retain the real package/build and worker observations, disclose this schema limitation and keep automatic closure incomplete; never manufacture image or commit identifiers.
