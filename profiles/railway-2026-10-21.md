# Optional profile: Railway environment-variable exposure of 2026-10-21

Last checked: 2026-10-22, while the incident was still open. This profile is a dated snapshot, not a standing rule. On every run, re-read the primary sources below and record their `retrieved_on` dates. If a source has changed, the source wins and this file is out of date.

## Primary sources

- Railway security disclosure: [Security Disclosure: Wednesday October 21st](https://blog.railway.com/p/security-disclosure-wednesday-october-21st)
- Railway status page for the incident: [status.railway.com incident QH8L8B3E](https://status.railway.com/incident/QH8L8B3E). It links Railway's per-provider follow-up guides (usage checks for AI and payment providers, access checks for GitHub and cloud accounts, database credential rotation).
- Railway guide: [Redeploy buckets and reconnect GitHub after the credential reset](https://blog.railway.com/p/security-disclosure-recommendation-redeploy-buckets-and-reconnect-github-after-the-credential-reset)
- For each credential you rotate: that provider's own documentation for revocation and audit logs.

## What was disclosed (as of the date above)

- An unauthorized third party may have accessed encrypted environment variables and, for some of them, obtained the decrypted values. Railway said its initial analysis suggests a subset of users, but asked all users to act.
- Railway's recommendation: roll every environment variable stored in Railway, including API keys and private registry credentials, and review logs for those services.
- Railway's own actions: rotated the credentials of every storage bucket, invalidated the GitHub tokens it held, removed GitHub registry tokens stored on services, invalidated all Railway API tokens and signed users out of OAuth sessions. Builds and deployments were paused for a period and restored in stages by plan tier.
- Not stated at the time of writing: the entry point, when access began, how many accounts were affected, and whether sealed variables were handled differently. Record each as UNKNOWN. Do not assume a workspace was outside the affected subset because it has not received an email.

## How this maps to the skill

This is a credential-exposure event (Phase 4), not a code vulnerability. Treat every value that was stored in Railway as exposed until it is rotated and the old value is revoked.

Targets to list in scope, linked with `related_targets`:

- the Railway workspace (`saas_tenant`): audit log, members, API tokens, GitHub connection
- each Railway service that held variables (`runtime`)
- each provider whose credentials were stored (`saas_tenant`): AI inference providers, payment providers, databases, cloud accounts, GitHub, container registries
- repositories and CI systems that hold copies of the same values (`repository`, `ci`)

## Inventory (read-only)

- For each project, environment and service: variable **names** only, shared variables, reference variables (`${{ service.VAR }}`), values pasted as plain text that duplicate a reference, registry credentials and bucket references. The dashboard and CLI can show values; capture names and redact anything else before it reaches a model, ticket or report.
- Railway API tokens used by CI, scripts or other integrations. All of them stopped working when Railway invalidated them, so failing integrations are expected.
- Copies outside Railway: `.env` files, CI secrets, developer machines and other hosts that hold the same values. `scripts/inventory.py` reports secret locations in a repository checkout without printing values.

## Closing a credential finding

A credential finding is `fixed` only when all of these are captured:

1. **New credential issued** at the provider, with a reference to the change (never the value).
2. **Deployed**: containers read variables at startup, so the service needs a redeploy after the change. Record runtime evidence that the new deployment is running (deployment ID and time after the rotation). If builds are paused for your plan, the check is BLOCKED and the finding stays open.
3. **Old value revoked at the provider**. Rotating a value inside Railway does not revoke it upstream. Example from Railway's guide: GitHub registry tokens removed from Railway still work on GitHub until you delete them there.
4. **Misuse review for the exposure window** in the provider's own logs: usage or billing spikes for AI providers, unexpected API calls or charges for payment providers, cloud and GitHub audit logs, objects added or deleted in buckets (Railway buckets have no automatic backups). No access to the logs makes this check BLOCKED, never "no misuse".

Other rules for this profile:

- Never test whether an old credential still works by using it. Use the provider's console or API listing to show it is revoked or deleted.
- Resets Railway performed (bucket credentials, GitHub tokens, API tokens) count as evidence that the old value stopped working at Railway. They still need the redeploy and misuse-review steps. Railway's guide says these resets appear in the workspace audit log under the actor type "Railway Staff"; that entry is expected, not misuse. Export the audit log entries you rely on, since retention depends on the plan.
- Revoking an old credential before the new one is deployed can cause an outage. Choosing the order is an owner decision; record the decision and who approved it.
- Database passwords, connection strings and cloud keys that were stored as variables are credentials too. Rotate them through the database or cloud provider, not only in Railway.

## What needs a human

Rotating and revoking every credential, choosing the rotation order, reviewing provider logs that need account access, notifying affected customers or partners, and deciding whether to keep using the platform.
