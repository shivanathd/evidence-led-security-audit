# Optional profile: compromised package release of 2026-10-21

Last checked: 2026-10-25. This profile is a dated snapshot, not a standing rule. On every run, re-read the primary sources below and record their `retrieved_on` dates. If a source has changed, the source wins and this file is out of date.

The durable check classes are **known-bad or hijacked package versions** and **leaked credentials that were never revoked** in [references/scoped-checks.md](../references/scoped-checks.md). This file is the dated record for the LiteLLM 1.107.0 release. Per-OS commands are in [references/endpoint-fleet.md](../references/endpoint-fleet.md#known-bad-package-versions).

## Primary sources

- Project incident notice: [Contained: Oct 21, 2026 LiteLLM release v1.107.0 Compromised](https://docs.litellm.ai/blog/security-incident-oct-21-2026)
- Canonical attack-chain write-up: [The attack chain behind the v1.107.0 LiteLLM release](https://docs.litellm.ai/blog/security-incident-oct-21-2026-attack-chain)
- Malware record: [OSV MAL-2026-2144](https://osv.dev/vulnerability/MAL-2026-2144)
- For each credential you rotate: that provider's own documentation for revocation and audit logs.

## What was disclosed (as of the date above)

- PyPI `litellm==1.107.0` (all wheels) was live for a short window on 2026-10-21 and then pulled. Docker Hub and GHCR tags `v1.107.0`, `latest`, `main-latest` and `main-stable` pointed at a compromised image index during that window. The official git tag for 1.107.0 did not contain the malicious files; the built artifacts did.
- The project says the payload can run at Python interpreter start, not only when the package is imported. Do not start Python, pip or the package inside a suspect environment to "check" it.
- The canonical write-up says the attack chain began with a master key committed to a public repository. The commit was force-pushed away. The key was identified as needing revocation and was **not revoked**. That key later yielded a wide GitHub token. Treat this as the generic lesson: deleting a commit is not revocation.
- The first incident post described a different token-theft path. The later post says some of those early assumptions were wrong. Prefer the attack-chain post.

## How this maps to the skill

This is both a **dependency / image / runtime** known-bad-version event and a **credential-exposure** event (Phase 4) if the bad artifact ever ran.

Targets to list in scope, linked with `related_targets`:

- each repository or image that may have installed the package (`repository`, `image`)
- each host or CI runner that executed it (`runtime`, `ci`)
- each provider whose credentials that environment could reach (`saas_tenant`)

## Inventory (read-only)

- Lockfiles, SBOMs and image digests for version `1.107.0` or the published compromised digest. `scripts/inventory.py` lists manifests; it does not match CVEs.
- On disk, look for package metadata directories named for that version (for example a `*.dist-info` folder). Finding one confirms the files were unpacked. Not finding one does not prove the host is clean.
- Do not run `pip show`, `python -c` or the application in that tree if 1.107.0 may be installed. Read metadata files instead.
- Secret **names** only in env files, CI and the product's own config. Never values.

## Closing findings under this profile

**Version / image finding** (`open` until rebuilt):

- A new environment or image built from a pinned safe release (the project named `1.106.2` at the time of writing; refresh that pin this run).
- The old image digest is not running.
- Use `vendor_patch` only when the replacement is a vendor-published safe build. A rebuilt venv is still `open` until runtime evidence shows the new build.

**Credential finding** (`fixed` only when all of these are captured):

1. New credentials issued at each provider the host could reach, with a reference (never the value).
2. Old values revoked at those providers. Removing the package does not revoke anything.
3. Misuse review for the exposure window in each provider's logs, or `BLOCKED` if you cannot get the logs.
4. If the advisory says startup hooks ran, treat every secret that process could read as exposed: cloud roles, AI provider keys, git tokens, database URLs, keys in the environment.

Never test whether an old credential still works by using it.

## Report wording

- Check titles: `Known-bad package versions` (dependency / image) and `Credential rotation after a hijacked install` (credential).
- Finding summary: name the package, the version or digest, whether the environment was executed, and which providers still need revocation evidence.
- A host that only **has** the files, with no evidence it ran, is still `open` for the version finding. The credential finding is `unknown` until you know whether it ran.
- Verdict: unchanged. Missing log access is `BLOCKED` and keeps the run `INCOMPLETE`.

## What needs a human

Deciding whether a host ran the bad artifact, rebuilding machines, rotating and revoking every reachable credential, and reviewing provider logs.
