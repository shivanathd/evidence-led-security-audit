# Optional profile: eMudhra intermediate CA key compromise of 2026-10-17

Reported to the root programs on 2026-10-17 and disclosed publicly on 2026-10-20. Last checked: 2026-10-25. This profile is a dated snapshot, not a standing rule. On every run, re-read the primary sources below and record their `retrieved_on` dates. If a source has changed, the source wins and this file is out of date.

For how to collect this evidence across many devices, see [references/endpoint-fleet.md](../references/endpoint-fleet.md).

## Primary sources

- Mozilla incident bug: [Bug 2083449, eMudhra: Private key compromise of Intermediate Certificates](https://bugzilla.mozilla.org/show_bug.cgi?id=2083449). It lists the eight intermediates with SHA-256 fingerprints, serials and issuers.
- Mozilla Security Blog: [Protecting Firefox users following the compromise of eMudhra intermediate certificates](https://blog.mozilla.org/security/2026/10/20/protecting-firefox-users-following-the-compromise-of-emudhra-intermediate-certificates/)
- eMudhra statement: [eMudhra Statement on Recent Certificate Security Incident](https://emudhra.com/en/post/certificate-security-incident)
- Apple: [About the compromised eMudhra intermediate CAs](https://support.apple.com/en-us/149555)
- Reporter's disclosure site: [emudhra.we-have-a-problem.com](https://emudhra.we-have-a-problem.com/). It publishes the affected certificates and their Sectigo cross-signs (`impacted-intermediates.json`), the roots they chain to (`roots.json`), test hosts and a table of patched software versions. It is not a vendor source: treat its version table as leads and confirm each package with its own vendor's advisory.
- For each trust store you rely on: that vendor's advisory or package changelog for the exact build.

## What was disclosed (as of the date above)

- The private keys of eight eMudhra intermediate CA certificates could be recovered from the certificates, because of a flawed key-generation step in a ceremony held in April 2025. Per the Mozilla bug, six are TLS intermediates (issued by emSign Root TLS CA - G3) and two are code-signing intermediates (issued by emSign Root CS CA - G3, trusted by Microsoft). Sectigo had cross-signed some of them; the reporter's list includes those cross-signs.
- eMudhra revoked all eight on 2026-10-18 and says none of them issued end-entity certificates. The reporter found no Certificate Transparency entries for them, so clients that enforce CT (Firefox, Chrome, Edge, Safari) could not have been attacked through them. Clients that do not enforce CT have no such assurance; whether anyone exploited them is unknown.
- Platform responses: Mozilla blocked the certificates through OneCRL on 2026-10-17, shipped Firefox 158.0.1 and ESR 115.43.1 and 153.5.1 for users with custom settings, and is removing the root that signed the intermediates from NSS in 3.131.1. Apple's page says devices have blocked the 12 TLS intermediate certificates (six plus their Sectigo cross-signs) since 2026-10-19, and `emSign ECC Root CA - G3` since 2026-10-23, for Safari, Mail and apps that use Apple's networking stack. Apple also says command-line tools that read `/etc/ssl/cert.pem` (curl, git, python3, ruby, perl, openssl) do not use that block until a future macOS update. The reporter's site states that Chrome blocked the intermediates on 2026-10-17 and Microsoft on 2026-10-20. eMudhra says the root programs distrusted its ECC root as a precaution.
- Clients that do not consume browser or OS revocation data keep trusting these chains until their own bundled roots are updated. That includes OpenSSL-style bundles shipped with the OS, language runtimes, JDKs, Electron apps and container base images.

## Exposure model

A client is exposed when it would accept a chain through any affected certificate (the eight intermediates or their cross-signs) and does not receive the platform blocks. Exposure is not compromise: there is no known misissued certificate. The risk is interception of traffic from non-CT clients by someone who holds a key.

Record exposure per client and store, not per device. A device can be protected in its browser and exposed in its command-line tools at the same time.

| Client or store | Protected by | Evidence to collect |
| --- | --- | --- |
| Firefox | OneCRL; Firefox 158.0.1 or ESR 115.43.1 / 153.5.1 for custom configurations | Browser version; probe result |
| Chrome, Edge, Safari and other apps on the platform verifier | Platform blocks from Google, Microsoft and Apple | OS and browser version; a live probe through the platform stack (`nscurl` on macOS, `Invoke-WebRequest` on Windows) and the reporter's in-browser checker in the user's own browser |
| macOS built-in `curl`, `git`, `python3`, `perl`, `ruby`, `openssl` | `/etc/ssl/cert.pem` only; no revocation checking | Whether either affected root is in the file; `/usr/bin/curl` probe |
| macOS built-in `pip` | Its own bundled roots | pip version or configured `cert`; probe through pip |
| Linux system store | Updated `ca-certificates` package, or a distrust entry | Package build and vendor advisory; distrust entries; probe |
| Windows | Microsoft's platform block (also covers the two code-signing intermediates) | `Disallowed` store contents; probe with a Schannel client |
| Java | Updated JDK release, or fingerprints added to `blocked.certs` | JDK version per install; `blocked.certs` contents; probe from Java |
| JetBrains IDEs, Toolbox, Gateway, ReSharper, bundled JBR, `jetbrainsd` | Product-specific floors on the 30 Oct 2026 JetBrains blog; OS updates do not cover these stores | Separate host check `jetbrains-jbr-emudhra` and [jetbrains-jbr-emudhra-2026-10-30.md](jetbrains-jbr-emudhra-2026-10-30.md). Do not treat an OS-store PASS as clearance for JBR |
| Python `certifi`, Node.js, Go, Rust, Electron, Docker Desktop, Homebrew `ca-certificates` | Updated release of each | Version per runtime against its vendor's advisory |
| Container images | Rebuilt image with an updated `ca-certificates` | Package build inside the deployed image digest |

On macOS both affected roots can still appear in the system root keychain while the platform blocks the intermediates. A root's presence in a store does not decide exposure; the probe does.

## Probing

The reporter's site provides test hosts that serve the affected chains, including one through the Sectigo cross-sign. Run them with each client type from the table above:

- Only a live connection from the client itself counts. Do not mark a client PASS from offline verification of saved chains: a live connection can build a different path through the cross-signs and soft-fail revocation checks, so offline and live results can disagree. See the live-probe table in [references/endpoint-fleet.md](../references/endpoint-fleet.md).
- Test every affected intermediate the reporter lists, not one per family. The intermediates can be protected differently on the same client.
- Rejected means a certificate-verification error (curl exit code 60). Before any change, an exposed client connects successfully; record that baseline.
- A timeout, DNS failure or proxy error is inconclusive and makes the check BLOCKED.
- Also probe a site that chains through Sectigo's current roots, so a change that breaks legitimate chains shows up.

## Interim measures

Prefer the vendor's updated package or release. Where none exists yet, each measure below is an owner decision, applied by the owner's management channel, never automatically:

- **macOS `/etc/ssl/cert.pem`**: remove the two root blocks (`AAA Certificate Services`, `emSign ECC Root CA - G3`), as the reporter's site describes. Write the new file beside the old one, check the certificate count dropped by exactly the removed blocks, then rename it into place; never truncate the live file first. Removing `AAA Certificate Services` can break private or legacy chains that end at it, so run the Sectigo probe afterwards. OS updates can restore the file, so re-check after each update.
- **macOS built-in pip**: point it at the fixed bundle with a site-wide `pip.conf` (`[global]` `cert = /etc/ssl/cert.pem`). Do not edit files inside Xcode or the Command Line Tools.
- **Linux before the package update**: the reporter's site gives distrust commands for the Debian and RHEL families and marks them as expert-only. Record them as a deviation from the vendor package and replace them with the vendor update when it lands.
- **Java before the JDK update**: append the affected SHA-256 fingerprints (uppercase hex, one per line) to each JDK's `blocked.certs`, after making sure the file ends with a newline. Restart running JVMs. JDK updates overwrite the file.

Record these as `mitigated`, with before and after probe evidence for each client. The skill's machine-checked closure chain is image-based (see the limits in README.md), so endpoint changes cannot be closed automatically; state that limit rather than inventing image fields.

## Closing a finding under this profile

For each client and store in scope, record:

- the installed build of the updated package or release, linked to that vendor's advisory, or the interim measure applied and who approved it
- a probe that succeeded before the change and is rejected after it, from the same client
- a passing probe to a legitimate Sectigo-chained site after the change
- fleet coverage: devices in scope, devices that reported, and the collection date (see `references/endpoint-fleet.md`)
- for container images, the package build inside the deployed image digest

## What needs a human

Choosing between waiting for vendor updates and applying interim measures, approving and running fleet scripts, deciding device scope and exclusions, and replacing any certificates your own services obtained from the affected hierarchy.
